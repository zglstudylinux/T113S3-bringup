## 1. 硬件连接(新原理图)

```
RTL8723DS 模块(U11)                    T113-S3
┌──────────────────┐
│ UART_IN          │◄──── PG6 (UART1_TX)
│ UART_OUT         │───── PG7 (UART1_RX)
│ UART_CTS         │◄──── PG8 (UART1_RTS)      四线 + 硬件流控
│ UART_RTS         │───── PG9 (UART1_CTS)
│ BT_DIS#(Pin34)   │───── R52 10kΩ 上拉 3V3(常使能,不接 MCU)
│ SUSCLK_IN(Pin24) │───── R91 10kΩ 上拉 3V3    ← RTL8723DS 需要(RTL8723BS 不需要)
│ VBAT_IN/VDDIO    │───── 3V3(C63 100nF/C64 10uF/C65 10uF)
└──────────────────┘
```

关键硬件事实:
- **无 MCU 复位脚**:BT_DIS# 硬件上拉,软件无法复位 BT 核心。**BT 核心复位 = VBAT 掉电 = 整板断电(必须含 adb USB 在内的所有供电,3V3 由任意一条 Type-C 喂)**——这是本文最重要的坑,见 §6.1;
- SUSCLK_IN 需要拉高(RTL8723DS 特性),硬件已由 R91 处理;
- HCI 走 UART1 四线(PG6-9),115200 起步,固件下载后切 1.5M。

### 3.6 rc.local:先 BT 后 WiFi 的开机时序

`openwrt/target/t113/t113-zgl_board/base-files/etc/rc.local` — 在音频 amixer 后、
`exit 0` 前插入(完整 diff):

```diff
--- a/base-files/etc/rc.local
+++ b/base-files/etc/rc.local
@@ -8,4 +8,36 @@
 amixer -Dhw:audiocodec cset name='ADC3 Gain' 19
 
+# RTL8723DS bring-up: BT FIRST, then WiFi.
+# The WiFi SDIO firmware download corrupts the module's BT ROM-download state,
+# and the module is always-powered with no reset GPIO, so BT (rtk_hciattach
+# downloads BT firmware over UART1) must run before 8723ds is loaded. The
+# 8723ds.ko is installed by kmod-net-rtl8723ds but intentionally NOT autoloaded.
+
+# Diagnostic: log whether 8723ds is already loaded and run BT in foreground
+# with full logging, waiting up to 30s for hci0.
+{
+	echo "=== rtl_bt_wifi: 8723ds loaded? ==="
+	lsmod | grep -c 8723ds || true
+	echo "=== rtl_bt_wifi: starting rtk_hciattach ==="
+	rtk_hciattach -n -s 115200 /dev/ttyS1 rtk_h5
+} > /tmp/bt_boot.log 2>&1 &
+BT_PID=$!
+
+for i in $(seq 1 30); do
+	[ -d /sys/class/bluetooth/hci0 ] && { echo "BT up after ${i}s" >> /tmp/bt_boot.log; break; }
+	sleep 1
+done
+
+# WiFi AFTER BT is up: the WiFi SDIO firmware download would otherwise corrupt
+# the module's BT ROM-download state (module is always-powered, no reset GPIO,
+# so a bad download state can only be cleared by a full power cycle).
+if [ -d /sys/class/bluetooth/hci0 ]; then
+	modprobe 8723ds && echo "=== rtl_bt_wifi: 8723ds loaded (after BT) ===" >> /tmp/bt_boot.log
+else
+	echo "=== rtl_bt_wifi: WARNING hci0 not up, 8723ds NOT loaded; full power-cycle required ===" >> /tmp/bt_boot.log
+fi
+
 exit 0
```

**为什么是这个顺序**:8723ds 的 WiFi SDIO 固件下载会破坏模块 BT 侧的 ROM 下载状态;
模块常供电、无复位脚,坏状态只能整板断电清除。所以必须 **BT 先 attach(下载 BT 固件)
→ WiFi 模块后加载**。`kmod-net-rtl8723ds` 故意无 AUTOLOAD 就是配合此时序(04-wifi.md §3.5)。

## 6. 排错记录(实际踩过的坑,含根因)

### 6.1 「断电」必须拔掉含 adb 线在内的**所有**供电(最重要)

原理图(`docs/sch/T113.md`):调试 Type-C(VIN5V)和供电 Type-C **都直接喂 3V3 轨**,
RTL8723DS 的 VBAT_IN/VDDIO 挂在 3V3 上。**只要任何一条 USB 线插着(包括 adb),模块就不断电。**

判断模块 BT 侧状态的指纹:

| 状态 | HCI Version | LMP Subversion | 波特率 | 结论 |
|---|---|---|---|---|
| ROM 干净态 | 0x08 | **0x8723** | 115200 应答 | 正常,hciattach 能完整下载固件 |
| 固件态(正常,固件在跑) | 0x07 | 0x6f72 | 1.5M | 正常!kit 文档 §5.1.1 确认 0x6f72 是 RTL8723D 固件态 |
| **被污染态** | 0x07 | 0x6f72 | 只在 1.5M 应答 SYNC 但 `IC: NONE`/`mismatch` | hciattach 期望 ROM 0x8723,校验失败,**任何软恢复无效** |

软恢复全部无效的原因:模块无复位脚(BT_DIS# 硬件上拉),SDIO 侧操作(unbind/mmc1
重枚举/WiFi 固件重下载)都不会复位 BT 核心。唯一手段 = **VBAT 掉电 = 拔所有线 30 秒**。

### 6.2 「手机搜不到设备」:hciattach 版本问题

锁版前(SDK 2017 plow 源码版)hci0 起来但 inquiry scan 不工作,手机搜不到。
锁版 100096B 后 `ACL MTU 1021` + `PSCAN ISCAN` 正常。判据:MTU 1021 = 对的版本。

### 6.3 「配对要 PIN」:btmanager 版本问题

4.0.5 源码编译版走 Numeric Comparison 要 PIN;4.0.3 prebuilt 免 PIN。
注意 4.0.3 的 `bt_manager_enable()` 不自己上电 adapter,`bt_init.sh` 补的
`hciconfig hci0 up` 是必要条件(§3.4)。

### 6.4 「重连蓝牙找不到设备」:bt_test 没在跑

`bt_test a2dp-sink` 死掉后 `PSCAN/ISCAN` 关闭、名字退化成 `RTK_BT_4.1`。
重新跑 §5.2 的 `start-stop-daemon` 命令即可。**不要**手动跑 `bt_init.sh start`
或手动 `hciconfig up` 干预——bt_test 启动时会 kill 已有 hciattach 并自己重新拉起,
手动干预会打乱它的初始化链路(实测踩坑)。

### 6.5 H5 sync timeout

`H5 sync timed out` 时先查 §6.1(模块状态被污染)。若刚烧录/刚换固件,
按 §6.1 断电流程后再试。开机时序不对(WiFi 先行)也会导致此现象。
